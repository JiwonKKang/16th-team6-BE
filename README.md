# 막차 경로 탐색 및 알림 서비스 "앗차!"

막차 놓치고 후회했던 경험, 다들 있죠?
**앗차는 복잡한 검색 없이, 막차 경로와 출발 타이밍을 똑똑하게 챙겨주는 
막차 알림 서비스입니다.**

# 챌린지

## 🚨 1. 막차 경로 검색 성능 최적화

서비스의 핵심 기능인 막차 경로 검색 API는 내부적으로 8개의 외부 API를 호출하는 복잡한 구조로, 초기에는 최악의 경우 15초 이상 소요되어 사용자 경험이 크게 저하되었습니다.

### ⚙️ 해결

1. **비동기 프로그래밍 적용:**
    - 독립적으로 호출 가능한 외부 API들을 코루틴을 통해 비동기 병렬 호출로 구현
    - 순차적 API 호출 방식 → 병렬 처리 방식으로 전환하여 전체 지연 시간 감소
2. **캐싱 및 중복 호출 제거:**
    - 앱 특성상 **유사 지역의 사용자들이 동일한 역/정류장 시간표를 조회한다는 패턴** 발견
    - 버스/지하철 시간표 데이터를 Redis에 캐싱
    - 막차 로직 내 불필요한 API 중복 호출 패턴을 발견하고 단일 호출로 리팩토링
    - 경로 결과 임시 캐싱으로 동일 쿼리 성능 향상

### 성과

- **초기 15초 이상 소요되던 처리 시간을 평균 2~3초로 개선 (약 80% 성능 향상)**
- 외부 API 호출 횟수 감소로 서비스 안정성 향상

### 배운 점

병목 지점을 정확히 파악하고 단계적으로 개선해 나가는 과정의 중요성을 배웠습니다. 성능 문제는 한 번에 해결되기보다 여러 개선점을 찾아 점진적으로 최적화하는 접근이 효과적임을 경험했습니다.

## 🚨 2. 복잡한 지하철 노선 구조 처리

지하철 노선의 복잡한 지선 구조로 인해 사용자의 출발역과 목적지역 간 정확한 도달 가능 경로 판단이 어려웠습니다. 공공데이터에서는 기점역, 종점역, 막차시간 데이터만 제공하여 사용자가 실제로 이용 가능한 막차인지 판단하기 어려운 상황이었습니다.

### ⚙️ 해결

1. **지하철 노선 구조 모델링:**
    - 외부 지하철 경로 API의 지선 구분이 불충분하여 도달 가능성 판단이 불가능한 문제 발견
    - 노선별 지선 데이터를 subway_branch 테이블로 구조화하여 저장
    - 각 지선별 운행 구간과 경유역 데이터 체계화
    - 종점역 기준 그룹핑을 통한 경로 도달 가능성 판단 로직 구현

### 성과

- 사용자의 실제 이용 가능한 정확한 막차 시간 정보 제공
- 잘못된 막차 정보로 인한 사용자 불편 최소화

### 배운 점

수도권 지하철 모든 노선의 경로를 직접 DB에 입력하여 구축하는 방법을 선택했습니다. 비효율적일 수 있지만, 제 책임을 다하기 위한 현실적인 해결책이었습니다. 때로는 정교한 알고리즘보다 직접적인 데이터 가공이 더 확실한 결과를 가져올 수 있다는 것을 배웠습니다.

## 🚨 3. 외부 API 의존성으로 인한 서비스 불안정성 문제

다수의 공공 API(서울, 경기도 버스/지하철 API)가 불안정하고 호출 횟수 제한이 있어 서비스 안정성이 저하되었습니다. 외부 API에 의존하다 보니 우리 서비스 서버에 문제가 아닌 외부 서버에서 잘못된 응답을 내려주는 경우도 자주 발생했습니다.

### ⚙️ 해결

1. **API 호출 안정화 전략 구현**:
    - 여러 API 키를 순환 사용하는 로테이션 전략 적용
2. **외부 API 오류 대응 로직 구현**:
    - 외부 서버에서 잘못된 응답(예: 누락된 막차 시간)을 보내는 경우 대체 로직 구현
    - 오류 데이터 발생 시 해당 버스/노선을 경로에서 제외하는 방어적 처리

### 성과

- 서비스 안정성 확보
- 외부 API 장애 상황에서도 부분적 서비스 제공 가능

### 배운 점

외부 API에서는 항상 정상적인 데이터가 내려오는 것은 아니라는 사실을 배웠습니다. 의존하는 시스템의 불안정성을 고려하여 항상 대비책을 마련해야 함을 깨달았고, 실제 운영 환경에서는 방어적인 코드 작성의 중요성을 경험했습니다.
